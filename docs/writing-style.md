# Korean Writing Style

Springfall 한국어 글의 문체 원칙입니다. `2026-07/setties`를 제외한 기존 한국어 글 56개 전체를 기준으로 잡되, 앞으로 글을 고칠 때 반복해서 확인할 수 있는 규칙으로 정리합니다.

## Corpus Summary

- 구어체 전환, 질문형 전환, 농담성 판단은 기존 글 대부분에 넓게 퍼져 있다.
- 기술 글은 요구사항, 불편함, 독자 상황을 먼저 좁힌 뒤 구현과 검증으로 간다.
- 에세이와 리뷰는 문제 해결보다 개인적 계기, 장면, 감정, 판단을 따라간다.
- 번역체 후보도 여러 글에 남아 있지만 하우스 스타일이 아니라 앞으로 교정할 대상이다.

## 목소리

- 번역된 매뉴얼처럼 쓰지 말고, 책상 앞에서 직접 설명하듯 쓴다.
- 대화체는 허용한다. `해봅시다`, `살펴볼까요`, `그렇다면`, `음...`, `흠`처럼 독자를 다음 단계로 데려가는 말은 Springfall의 안정적인 리듬이다.
- 다만 방송 진행자처럼 문장을 계속 매달지는 않는다. `문제는요,`처럼 쉼표로 끄는 표현은 글쓴이 목소리가 살아날 때만 쓰고, 새 글에서는 `문제는 여기서 시작합니다`, `가장 기본적인 문제부터 보죠`, `가장 기본적인 문제는요? 바로 ...입니다`도 검토한다.
- 딱딱한 설명 뒤에는 짧은 개인 판단이나 감각을 붙여도 된다. 기술 글이어도 글쓴이의 목소리가 남아야 한다.
- 자신의 한계와 판단 근거를 드러낸다. 확신만 밀어붙이기보다 “여기까지는 확실하고, 여기는 아직 불안하다”를 분리해서 쓴다.
- 오래된 글의 `필자`, `녀석`, `놈`, 과한 밈, 욕설, 초캐주얼 엔딩은 기본값으로 삼지 않는다. 글 성격에 붙은 장식으로만 본다.

## 문장

- 추상 명사형보다 한국어 동사로 말한다.
  - Prefer: `schema가 있습니다`
  - Avoid: `schema를 가집니다`
  - Prefer: `수정됩니다`
  - Avoid: `수정이 수행됩니다`
- `것`, `것들`, 불필요한 복수 `-들`은 줄인다. 단수 명사가 일반 의미를 이미 담을 수 있으면 단수로 둔다.
  - Prefer: `파일이 제대로 symlink 되어 있는지`
  - Avoid: `파일들이 제대로 symlink 되어 있는지`
  - Prefer: `바뀌는 지점`
  - Avoid: `변동되는 것들`
- 실제 여러 사람이나 집단을 가리키거나 복수 대비가 의미를 만들 때는 `-들`을 남긴다.
  - OK: `독자들`, `동료들`, `사람들`
  - OK: 여러 환경의 값이 서로 다를 때 `값들이 달라`
- `~것`을 무조건 금지하지 않는다. 빼서 문장이 더 어색해지면 남긴다.
- 피동과 이중 피동을 줄인다.
  - Prefer: `담겨 있고`
  - Avoid: `담겨져 있고`
  - Prefer: `소중하게 생각했으면`
  - Avoid: `소중하게 생각되어졌으면`
- `~을 통해`, `~에 대해`, `~을 위해`가 보이면 더 짧은 조사나 동사로 줄일 수 있는지 먼저 본다.
- 부풀린 설명보다 직접적인 표현을 고른다.
  - Prefer: `현재 상태와 기대 상태의 차이를 보이게 만드는 것`
  - Avoid: `현재 상태와 기대 상태 사이에 존재하는 차이에 대한 가시성을 제공하는 것`

## 기술어

- 익숙한 영어 기술어는 억지로 번역하지 않는다. `repo`, `schema`, `pre-commit`, `symlink`, `command`, `file`, `dir`처럼 그대로 쓰는 편이 자연스러울 때가 있다.
- 글의 중심이 되는 영어 기술어는 처음 한 번 한국어 설명을 붙인다.
  - 예: `환경변수(Environment Variables)`
  - 예: `CLI(Command Line Interface)`
  - 예: `Hot Module Replacing(이하 HMR)`
  - 예: `Homebrew: 패키지 매니저`
- 이후에는 원어, 약어, 제품명을 유지한다. 매번 풀어쓰지 않는다.
- 코드, 옵션, 파일명, 환경변수, 식별자는 원문 그대로 두고 백틱으로 고정한다.
  - 예: `.zshrc`, `NEXT_PUBLIC_XXX`, `env.js`, `eslint --fix`
- 영어 단어와 한국어 조사는 현업식 혼용을 허용한다. 다만 조사와 띄어쓰기가 흔들리면 마지막에 정리한다.
  - OK: `Flat Config로 가겠습니다`, `Router에서는`, `ESLint 에러`
- 표기는 고정한다.
  - `JavaScript`, `TypeScript`, `타입스크립트`
  - Avoid: `Javascript`, `Typescript`, `타입스트립트`

## 구성

- 글의 시작점은 글 유형에 맞춘다.
  - 기술 글: 요구사항, 불편함, 독자 상황, 실패 사례에서 시작한다.
  - 절차형 글: 기준 환경, 순서, 다루지 않는 범위를 먼저 둔다.
  - 에세이와 리뷰: 개인적 계기, 장면, 감정, 질문에서 시작한다.
- 처음부터 개념 정의로 밀어붙이지 않는다. 정의가 필요하면 구체적인 상황을 먼저 보여준 뒤 붙인다.
- 독자가 가질 만한 의문을 먼저 말해도 좋다.
  - 예: `왜 className을 금지하는 ESLint 규칙이 필요할까요?`
  - 예: `환경변수란 무엇일까요?`
- 기술 튜토리얼의 기본 골격은 `요구사항/상황 -> 문제 핵심 -> 설계 선택 -> 구현 -> 검증 -> 한계`다.
- 개념 설명 글은 `목표/사전지식 -> 개념 -> 예시 -> 요약` 흐름이 잘 맞는다.
- 실패와 한계는 학습 장치다. 실제로 배울 점이 있으면 숨기지 않는다.
- 주장 뒤에는 근거를 붙인다. 근거는 글 유형에 맞게 고른다.
  - 기술 글: 코드, 표, 스크린샷, 데모, 실행 로그, 테스트 결과.
  - 에세이/리뷰: 장면, 기억, 인용, 감각, 자기 판단.
- 목록은 훑어보기 좋게 쓰되, 각 항목은 짧고 주장처럼 보이게 쓴다.
- 현재 글의 맥락에 맞지 않는 이야기는 덜어낸다. 별도 글감으로 남기는 편이 낫다.
- 결론은 과하게 닫지 않는다. 요약, 한계, 다음 행동, 여운, 농담성 마무리 모두 글 성격에 따라 가능하다.

## 근거로 삼은 기존 패턴

- 전체 한국어 글 56개에서 구어체/질문 전환은 53개 글에 반복된다.
- 전체 한국어 글 56개에서 예시, 가정, 비유는 46개 글에 반복된다.
- 전체 한국어 글 56개에서 코드, 이미지, 표, 컴포넌트 기반 근거는 800회 이상 등장한다.
- `why-writing`: 말하는 대로 쓰기, `~것` 지양, 어려운 말 풀어쓰기, 구체적인 어휘 발굴.
- `node-js-stream`, `easy-promise-async-await`: 독자를 데리고 가는 질문형 기술 설명.
- `check-target`, `workflow`, `live-editor`: 요구사항에서 시작해 구현과 검증으로 가는 기술 글 구조.
- `mac-settings`: 절차형 글에서 기준 환경과 순서를 먼저 제공하는 방식.
- `belief`, `family`, `geultto`, `nakwon`: 개인적 계기와 감정에서 출발하는 에세이 구조.
- `nextjs-inject-env`, `farming-paper`, `ga`, `zod`: 영어 기술어를 처음만 설명하고 이후 원어로 유지하는 방식.

## Revision Checklist

- 이 문장이 번역문이 아니라 글쓴이가 직접 말하는 것처럼 들리는가?
- 글의 시작점이 유형에 맞는가: 문제, 요구사항, 기준 환경, 개인적 계기 중 무엇인가?
- `것`, `것들`, `-들`을 빼도 의미가 유지되는가?
- `가집니다`, `가지고 있습니다`, `갖고 있습니다` 같은 소유 표현을 `있습니다`, `합니다`, `담습니다`, `씁니다`로 바꿀 수 있는가?
- 피동 표현을 능동적인 한국어 동사로 줄일 수 있는가?
- 영어 기술어가 필요한가? 필요하다면 첫 설명, 백틱, 표기가 충분한가?
- 기술 글은 구현이나 주장 뒤에 검증 근거가 있는가?
- 에세이와 리뷰는 각 섹션이 계기, 감정, 질문, 판단 중 하나로 이어지는가?
